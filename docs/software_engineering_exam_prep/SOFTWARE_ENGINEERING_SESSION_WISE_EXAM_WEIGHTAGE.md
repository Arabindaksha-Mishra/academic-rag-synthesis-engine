## 3. In-Depth Breakdown of Post-Midterm High-Yield Sessions (CS08 to CS16)

### Session 08: Architectural Design and Styles
* **Weightage**: 4 – 8 Marks | **Priority**: Tier 1 (Critical)
* **Core Topics in Syllabus**:
  - Architectural Styles: Data-centered (Repository), Data-flow (Pipes and Filters), Call and Return (Layered architecture), Object-Oriented, Event-Driven.
  - Architectural Patterns: Model-View-Controller (MVC), Client-Server, Microservices.
  - Architectural Trade-offs: Modifiability, performance, security, availability.
* **How It Is Tested**:
  - Selection and justification of an architectural pattern (e.g., MVC for Doctor's web portal in Q1b).
  - Mapping specific case-study functional requirements to architectural layers (Model = database/rules, View = UI/presentation, Controller = request dispatching & session validation).
* **Common Pitfall**: Giving generic textbook definitions of MVC without explicitly identifying which entities in the scenario belong to Model, View, or Controller.

---

### Session 09: Component-Level Design & WebApps
* **Weightage**: 8 – 12 Marks | **Priority**: Tier 1 (Super Critical — Highest Yield)
* **Core Topics in Syllabus**:
  - Nature of a Component: Object-oriented, conventional, and process-related views.
  - Class-Based Component Design: Elaboration of attributes, operations, and interfaces.
  - Design Principles: Open-Closed Principle (OCP), Liskov Substitution Principle (LSP), Dependency Inversion Principle (DIP), Interface Segregation Principle (ISP).
  - WebApp Component Design: Asynchronous communication, offline synchronization, chunked file upload over low-bandwidth / high-latency networks.
* **How It Is Tested**:
  - Direct design question: "Detail the steps involved in Component-Level Design for a Class-Based Component..." (Q1a: 5 Marks).
  - "Specify two key attributes and three operations for the primary class..." (e.g., `PaymentTransactionManager`).
  - WebApp robustness under hostile network conditions (Q1c: 4 Marks: PDF diagnostic report upload over 2G/3G rural networks).
* **Common Pitfall**: Leaving attributes untyped or methods without arguments/return types. Omitting the algorithmic/procedural detail of how error handling and idempotency work.

---

### Session 10: User Interface Design and Heuristics
* **Weightage**: 5 – 8 Marks | **Priority**: Tier 1 (Critical)
* **Core Topics in Syllabus**:
  - Theo Mandel’s 3 Golden Rules:
    1. Place the User in Control.
    2. Reduce the User's Memory Load.
    3. Make the Interface Consistent.
  - UI Design Process: Interface analysis, design modeling, construction, and validation.
  - Usability Heuristics (Nielsen): Visibility of system status, match between system and real world, user control and freedom, error prevention, recognition rather than recall.
* **How It Is Tested**:
  - Wireframe drawing: "Design the initial wireframe for the Patient Interface Home Screen..." (Q2a: 5 Marks).
  - Interface critique: Must explicitly select and apply 3 Golden Rules to critique the drawn wireframe in the context of the target demographic (e.g., rural, low digital literacy).
* **Common Pitfall**: Drawing an unlabelled box diagram without clear navigational elements, language toggles, or emergency shortcuts, and failing to map each UI element to a specific Golden Rule.

---

### Session 11: Design Patterns (Creational, Structural, Behavioral)
* **Weightage**: 5 – 8 Marks | **Priority**: Tier 1 (Critical)
* **Core Topics in Syllabus**:
  - Pattern Classification: Creational (Factory, Singleton, Builder), Structural (Adapter, Facade, Decorator, Proxy), Behavioral (Observer, Strategy, Command, State).
  - Pattern-Based Design: Reusability, decoupling, and domain translation.
* **How It Is Tested**:
  - Justifying MVC or suggesting a secondary pattern for asynchronous event handling, telemetry, logging, or gateway bridging (Q1b: Suggesting Observer Pattern for real-time consultation queue alerts or Adapter Pattern for multi-bank payment gateways).
* **Common Pitfall**: Naming a pattern without explaining the participant classes (Subject/Observer or Target/Adaptee) and how they communicate.

---

### Session 12: Software Testing Strategy and Process
* **Weightage**: 4 – 6 Marks | **Priority**: Tier 1 (Critical)
* **Core Topics in Syllabus**:
  - Testing Hierarchy: Unit Testing -> Integration Testing (Top-Down, Bottom-Up, Sandwich) -> Validation Testing -> System Testing (Recovery, Security, Stress, Performance).
  - Verification vs. Validation: Boehm's distinction ("Building right product" vs. "Building product right").
  - Validation Testing Strategies: Alpha/Beta testing, acceptance criteria, operational compliance.
* **How It Is Tested**:
  - "Develop a Validation Testing Strategy... identify three distinct validation testing activities and specify a quantifiable criterion (latency, error rate, throughput) for each" (Q3a: 4 Marks).
* **Common Pitfall**: Stating vague criteria like "system should be fast" or "no bugs" instead of quantifiable engineering metrics like "latency <= 2.5 s on 3G", "payment reconciliation accuracy = 100%".

---

### Session 13: Testing Methods: White-Box and Black-Box
* **Weightage**: 4 – 8 Marks | **Priority**: Tier 1 (Critical)
* **Core Topics in Syllabus**:
  - White-Box Testing (WBT) / Glass-Box: Basis Path Testing, Control Flow Graphs (CFG), Cyclomatic Complexity ((G) = E - N + 2P$), Condition Testing, Data Flow Testing.
  - Black-Box Testing (BBT) / Behavioral: Equivalence Partitioning (EP), Boundary Value Analysis (BVA), Orthogonal Array Testing, Cause-Effect Graphing.
* **How It Is Tested**:
  - Distinguishing WBT and BBT and selecting 1 specific technique from each category to apply to a critical module (Q3b: Basis Path Testing for payment branching logic + BVA for transaction currency limits).
  - Possible mathematical question: Constructing CFG, computing Cyclomatic Complexity (G)$, and enumerating independent execution paths.
* **Common Pitfall**: Confusing White-Box with Unit Testing (WBT is a *methodology*, Unit Testing is a *phase*). Forgetting the 3 formulas for Cyclomatic Complexity.

---

### Session 14: Software Quality Assurance (SQA) & Reviews
* **Weightage**: 8 – 12 Marks | **Priority**: Tier 1 (Super Critical — Highest Yield)
* **Core Topics in Syllabus**:
  - Quality Concepts: McCall’s Quality Factors (Product Operation, Revision, Transition), Garvin’s 8 Dimensions.
  - SQA Activities Beyond Testing: Formal reviews, automated static analysis (SAST/DAST), code audits, standard operating procedures, compliance verification (DPDP, HIPAA).
  - Formal Technical Reviews (FTR): Review roles (Leader, Producer, Reviewer, Recorder), preparation guidelines, meeting conduct, FTR report and review issue list.
* **How It Is Tested**:
  - Two distinct quality concepts critical to domain + 3 specific SQA activities beyond testing (Q2b: 5 Marks).
  - Formal Technical Review: Required participants, roles, and review meeting objectives (Q2c: 5 Marks).
* **Common Pitfall**: Listing testing activities (e.g. regression testing, unit testing) when the question specifically demands *activities beyond testing*.

---

### Session 15: Project Management, Estimation & Risk
* **Weightage**: 3 – 8 Marks | **Priority**: Tier 2 (High)
* **Core Topics in Syllabus**:
  - The 4 Ps of Software Project Management: People (stakeholders, team organization), Product (scope, decomposition), Process (SDLC framework, milestones), Project (planning, tracking, risk).
  - Software Estimation: Function Points ( = 	ext{Count Total} 	imes [0.65 + 0.01 	imes \sum(F_i)]$), COCOMO I & II models ( = a 	imes (	ext{KLOC})^b$).
  - Risk Management: Reactive vs. Proactive, Risk Identification, Risk Projection, RMMM Plan (Risk Mitigation, Monitoring, and Management).
* **How It Is Tested**:
  - Analyzing a case study across the 4 Ps in a specific geographical/regulatory context (Q3c: 3 Marks).
  - Potential calculation question on Function Points ($) or Cyclomatic Complexity.
* **Common Pitfall**: Treating the 4 Ps as generic management concepts rather than addressing software engineering and deployment constraints.

---

### Session 16: Emerging Trends & DevOps
* **Weightage**: 0 – 3 Marks | **Priority**: Tier 3 (Low)
* **Core Topics in Syllabus**:
  - DevOps culture, CI/CD pipelines, Continuous Integration, Automated Deployment.
  - Software maintenance, reverse engineering, re-engineering.
* **Exam Role**: Typically tested as secondary sub-points inside SQA or process questions (e.g., CI/CD static code analysis pipelines).

## 4. Foundational Pre-Midterm Sessions (CS01 to CS07)

While pre-midterm sessions rarely appear as standalone primary questions in comprehensive exams, **Session 07 (Design Concepts)** is indispensable because its principles underpin Session 09 and Session 08 questions.

### Session 07: Software Design Concepts & Principles
* **Exam Relevance**: **Universal Foundation** (appears in Q1a and design questions).
* **Must-Know Concepts**:
  - **Cohesion (Aim: High / Functional)**:
    - *Functional Cohesion* (Ideal): Component performs one well-defined mathematical or business action.
    - *Sequential / Communicational Cohesion*: Steps operate on the same data stream.
    - *Procedural / Temporal Cohesion*: Grouped by order or time of execution.
    - *Coincidental Cohesion* (Worst): Arbitrary grouping with no logical relationship.
  - **Coupling (Aim: Low / Loose)**:
    - *Data Coupling* (Ideal): Components pass only simple primitive data arguments or DTOs.
    - *Stamp Coupling*: Passing composite data structures where only a subset of fields are used.
    - *Control Coupling*: One component passes a flag directing the internal logic of another.
    - *Common Coupling*: Components share global memory or database tables.
    - *Content Coupling* (Worst): One component directly accesses or modifies another module's internal code or private state.
  - **Information Hiding**: Modules expose abstract public interfaces while encapsulating internal state and algorithmic mechanics.
